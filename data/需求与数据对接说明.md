## 2. 销售口径与导入

### 已确认口径

| 模式 | 门店销售金额 | 核心销售总额 |
| --- | --- | --- |
| 真实模式 | 所选业务日期的真实门店订单净额，不加基数 | 历史数据包含零售＋批发；本版手工今日导入只接门店主表，标题显示“今日销售额”，工具栏明确该批仅为今日门店订单 |
| 演示模式 | 该门店日均基数＋人工导入今日门店订单净额 | 当前全业务演示基数＋逐笔播放的订单增量；批发今日导入仍待扩展 |
| 未导入今日订单时 | 使用已有历史订单作为回放样例 | 回放源默认 2026-10-03，原始业务日期不改写；页面工具栏保留模式和日期 |

“今日订单”由人工导表导入，不代表已接入 ERP 接口、自动拉取昨日数据或自动改变原始日期。日期转换只能发生在明确的演示副本，不能覆盖源文件。

试营业期间 2026-09-24 至 2026-10-03，首尾计入为 **10 天**。日均销售基数＝对应金额合计÷10。用户指定原表 F 列销售金额；正式替换时必须映射实际金额字段，不能将销售数量当金额。已核对：总额 417,280.88 元，日均 41,728.088 元；其中门店零售 279,643.04 元 / 27,964.304 元，批发 137,637.84 元 / 13,763.784 元。显示保留两位小数，计算保留原精度。

### 本版今日门店订单导入

配置页 → 数据导入 → 选择 XLSX / XLS / CSV → 选择工作表及表头行 → 映射订单号、门店编码、净销售金额、业务日期 → 核对预览 → 应用导入。

- 表头可以变化，列位置不写死。导入订单主表，禁止将商品明细行金额重复作为整单金额。
- 仅接受业务日期为当前上海时区今日的记录；不在已确认门店清单内的编码、缺少订单号、无效金额会阻止整批应用。
- 以门店编码＋订单号去重；相同订单内容重复只计一次，相同订单号金额不同则要求核对。
- 净销售金额按源字段正负累计，退单保留负数；没有自动推断正数退单的功能，映射前必须确认金额符号。
- 应用时替换整批今日订单，不重复叠加同一份导出。再次导入更完整的当日主表可更新销售金额。
- 今日订单只保存在当前浏览器，不会改变同事所见的公共快照。跨电脑共享最新导入结果需要管理端、共享存储和发布流程。
- 试营业基数替换入口仍是映射规则预览；正式基数解析保存、类别销售表、订单明细及批发今日数据导入待后续实现。

### 今日销售额跳动与“vs 昨日”

- 标题按要求改为“今日销售额”，移除右侧“基数＋订单”标签。未导入今日数据时，演示模式使用历史订单；真实历史预览仍标明“历史日净销售额”，不把过去某日改称真实今日。
- 演示模式每隔配置秒数累计一张订单，今日导入也按此方式播放。所有订单累计完后，流水继续循环显示，但已播放订单不再次加钱；更完整的新文件导入后替换整批并重新播放。
- 第一列演示时间为单独生成的展示时间（上海时区，秒级），原始业务日期与时间不改写；真实模式保留源订单时间。流水显示3条，不显示样例计数。
- 用户确认“昨日金额”采用试营业日均销售基数作为比较分母，是指定的比较基准，**并非昨日实际订单金额**。比例＝（当前销售额－同业务范围日均基数）÷同业务范围日均基数×100%。正值▲、负值▼，分母缺失或不大于0时显示“—”。
- 演示全业务分母为41,728.088元；今日真实导入当前只含门店，因此分母采用门店日均27,964.304元，避免拿部分业务销售额与全业务基数作比较。
- 手工导出的固定文件不会产生新的真实业务记录；要更新真实金额，需要再次导入最新当日订单。今后接ERP接口／定时同步后，才可自动刷新真实数据。

## 5. 已选和风天气，按免费额度接入

用户指定免费方案，并选择和风天气。目前没有提供API Host或账户凭据，尚未接入真实天气，页面仍为天气与需求/农业联动排版样例。底部折线图从约96设计像素缩为48，减少一半；联动建议规则需要业务确认。

[和风官方价格表](https://dev.qweather.com/docs/finance/pricing/)当前规定：天气和基础服务分组每自然月前50,000次请求费用为0，之后收费；额度按该组各服务请求总量累计，不是每个网页访问者各有50,000次。**免费额度不等于无限免费。**

接入步骤：

1. 创建和风账号与项目，获取API Host，并按[项目和凭据文档](https://dev.qweather.com/docs/configuration/project-and-key/)设置JWT认证。先提供API Host、目标地点与脱敏响应样例；私钥在服务器密钥设置中保存，不放公开HTML或仓库。
2. 后台调用实况和[每日预报](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)，取7天；公开大屏只读后台统一缓存，不让每个电脑都调用上游。
3. 可先按每小时各取一次实况与7天预报，31天约1,488次请求；其他同账户项目的调用也会影响免费额度。设调用预算、缓存和限频，接近额度时暂停新增上游调用，保留最后有效数据和更新时间；不自动使用收费服务。
4. 天气日期统一上海时区；和风逐日路径为/weather/v1/daily/{latitude}/{longitude}，纬度在前，默认7天、可指定days=7、localTime=true。地图数据仍为[longitude, latitude]，仅适配层转换顺序。
5. 接口失败显示最近有效数据的时间，未取得任何成功数据时显示缺失；不把样例静默当实况。按接口返回信息注明和风来源。需求与农业建议由业务规则产生，天气接口本身不提供销量预测结论。

以上为接入方案，后台缓存、额度限制与真实API调用尚未实施，待公开托管与账号配置确定后完成。

## 6. 跨电脑访问与更换数据

`file:///Users/...` 是本机文件路径，其他电脑不能通过该路径访问。最终需要公开 HTTPS 站点，访问权限设置为任何拿到链接的人可看，不要求登录。

本版已准备完整静态网站和单文件HTML，并新增GitHub Pages专用发布包。用户希望使用GitHub Desktop，可按《GitHub-Desktop与Pages发布步骤.md》创建Public网页仓库并开启Pages；原始ERP文件可另存Private数据仓库。当前尚未创建用户GitHub远端仓库或完成Pages部署。此前Sites项目已登记，但还没有部署成功的版本。2026-10-05 再次发布时，工具自动审批拒绝传入发布流程所需凭据：`write_stdin rejected: approval required by policy, but AskForApproval::Granular.sandbox_approval is false`。因此当前没有可提供给同事的已发布网址。

短期可将单文件 HTML 发给同事，让他们下载后在自己电脑打开；这只是临时文件评审方式。正式共享网址需要完成Pages等公开托管发布，并从未登录的其他电脑验证。仓库可以保存文件和版本；持续共享订单仍需开发导入、校验、生成公开汇总数据的发布流程。

后续建议保留代码仓库＋共享数据存储：代码、字段映射及版本在私有仓库维护；原始导出表和上传批次保存在托管平台存储，后台生成供网页读取的汇总数据。GitHub不是每日上传业务表的必要前提，也不应把原始业务 Excel 直接放公开仓库。使用托管平台存储通常无须另办独立“云盘账号”，但需要所选托管服务账号及相应存储配置。

更换表格的流程应为：管理员上传 → 选择报表类型及日期 → 映射新表头 → 检查金额、主键、重复、日期、分类及总额 → 确认批次 → 写入共享存储 → 所有电脑读取相同数据版本。公共展示与有权限的管理上传入口需分开；公开查看不意味着任何访客都能修改共享数据。
